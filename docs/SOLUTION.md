# LP-0002 Solution Write-up — Private M-of-N Multisig

Single-document write-up for evaluators: threshold proof scheme, nullifier
design, LEZ account model compatibility (nonce + `program_owner`), security
assumptions, known limitations, integration instructions.

## Threshold proof scheme

The scheme is Semaphore-pattern anonymous signalling implemented natively for
the LEZ privacy-preserving transaction model — not FROST/threshold-signature
aggregation, and not a port of Semaphore's circuits.

- **Registration.** Each member's secret is their shielded account's
  nullifier secret key (`nsk`), HD-derived by their wallet
  (`SeedHolder → SecretSpendingKey → produce_private_key_holder(i)`). At
  `initialize`, only one-way commitments
  `C_i = SHA256("member" || nsk_i || multisig_id)` are registered on-chain,
  along with the threshold M.
- **Anonymous approval.** A vote is a privacy-preserving transaction whose
  initial call is the multisig program's `Vote` instruction. Initial-call
  instruction data is a private witness in LEZ, so the nsk and the member
  index never leave the voter's machine. In-circuit the program recomputes
  `SHA256("member" || nsk || multisig_id)` and requires it to equal the
  registered commitment at the claimed index. The proof can only be produced
  by a holder of a registered nsk; the chain learns only that *some*
  registered member voted.
- **Threshold gating.** Each valid vote appends a nullifier and increments a
  public `vote_count`. `Execute` requires `vote_count >= M` in-program. The
  threshold is enforced by counting distinct nullifiers, so M approvals
  really are M distinct members (see nullifier design).
- **Live-account binding** (beyond derivation-only): the vote transaction
  carries the member's shielded voting account as its private rider. The
  guest asserts `rider.account_id ==
  AccountId::for_regular_private_account(npk(nsk), 0)` and
  `rider.account != Account::default()`; the LEZ privacy circuit proves the
  rider's pre-state commitment is in the live commitment tree and rotates it
  like any private transfer. An approval therefore requires control of a
  live shielded account enrolled in the member set, and the vote is
  indistinguishable from ordinary shielded traffic.

## Nullifier design

`N = SHA256("multisig/v1/vote" || nsk || proposal_id || multisig_id)`

- One nullifier per (member, proposal, multisig) triple: a second vote by the
  same member on the same proposal reproduces the same N and aborts
  in-circuit (`ERR_6004`) — the proof cannot be generated, so a double vote
  never even reaches the chain.
- Domain separation (`"multisig/v1/vote"`) keeps vote nullifiers disjoint
  from every other SHA256 use in the system, including the member
  commitments (`"member"` domain) and LEZ's own account-update nullifiers.
- Unlinkability: without the nsk, N is uniformly random and cannot be linked
  to any commitment C_i; nullifiers are independent across proposals and
  across multisig instances (both ids are mixed in).

## LEZ account model compatibility

**The nonce constraint.** LEZ private accounts increment their nonce and
rotate their commitment on every use, so the lez-multisig PoC's approach —
members are fresh zero-nonce keypairs claimed by the program — cannot work
for shielded accounts. Here, members never *spend* to vote and the program
never claims a member account: the member's shielded account participates as
the privacy-transaction rider, whose nonce/commitment rotation is performed
by the LEZ privacy circuit itself, exactly as in a private transfer. Voting
is a normal use of the account, not a violation of its lifecycle.

**The `program_owner` constraint.** Programs can only mutate accounts they
own. The design splits state and identity:

- The **multisig account** (all governance state: threshold, commitments,
  proposals, nullifier sets) is a public account claimed by the program at
  `initialize` via `Claim::Authorized` — the one and only signature in the
  whole lifecycle, made with a throwaway key generated by
  `multisig chain keygen`. After the claim it is program-owned:
  `submit-proposal`, `vote` and `execute` are unsigned.
- The **member's voting account** stays owned by the LEZ privacy protocol
  (as all private accounts are). The program never claims or mutates it — it
  passes through as an unchanged post-state and the privacy circuit performs
  the rotation.

## Security assumptions

See [SECURITY.md](SECURITY.md) for the full threat model. Summary: RISC0
Groth16 ceremony (all of LEZ trusts it), SHA256 as a random oracle for
commitment/nullifier hiding, the LEZ privacy circuit's commitment-membership
proof for the rider binding, and the sequencer for liveness (not for
integrity: proofs are client-side and nullifiers prevent replay).

## Known limitations

- Anonymity set is at most N (inherent to small-N multisig).
- Member set is fixed at initialization; rotation requires a new instance.
- `execute` finalizes the proposal's action bytes (a threshold-gated
  parameter change readable by downstream programs); it does not chain-call
  into a target program (v2 roadmap).
- Votes on the same proposal serialize (each proof commits to the multisig
  pre-state, so two simultaneous votes race for the same post-state; the
  loser re-proves).

## Integration instructions

- **CLI**: complete lifecycle walkthrough in the [README](../README.md)
  (deploy → member identities → initialize → propose → vote → execute →
  state reads).
- **SDK** (`sdk/`): the instruction set (`MultisigInstruction`), state types
  and decoders (`decode_state`, `render_state`), and the derivation functions
  (`derive_commitment`, `vote_nullifier`) — everything a Logos module needs
  to build instructions and read multisig state without the CLI. Transaction
  submission uses the LEZ `wallet` crate (`WalletCore`): public transactions
  for initialize/propose/execute, `send_privacy_preserving_tx` with accounts
  `[PublicNoSign(multisig), PrivateOwned(voting_account)]` for votes.
  `cli/src/main.rs` is the reference client.
- **IDL**: [lp-0002-private-multisig.idl.json](../lp-0002-private-multisig.idl.json)
  (SPEL IDL) describes instructions, account layouts and error codes.
- **Basecamp app**: `basecamp-app/` with build/load instructions and
  downloadable release assets.
- **Benchmarks**: [BENCHMARKS.md](BENCHMARKS.md) — proof generation time and
  per-operation compute (RISC0 cycle counts).
- **Testnet evidence**: [TESTNET_EVIDENCE.md](TESTNET_EVIDENCE.md) — program
  id, multisig instance, full 2-of-3 lifecycle transaction hashes on
  `https://testnet.lez.logos.co` (LEZ v0.2.0).
